## ۲. یافته‌های تحقیق (قطعی، با آزمون زنده)

### ۲.۱ اتصال به کرومِ بازِ کاربر — ✅ تأیید شد

آزمون زنده روی همین سیستم انجام شد و **موفق بود**:

```
CONNECTED. browser.version -> 153.0.8010.48
existing browser contexts: 1
existing pages in context[0]: 7
live fill/read round-trip -> 'omni-ok'
```

**چرا کار می‌کند:** کروم ۱۵۳ روی این سیستم در «حالت تأیید» (approval mode) است — prefs `devtools.remote_debugging.user-enabled: true`. این قابلیت از دسامبر ۲۰۲۵ فعال شده.

**نکته‌ی مهم معماری:**
- محدودیت امنیتی کروم ۱۳۶ به بعد، فلگ `--remote-debugging-port` را روی پروفایل پیش‌فرض **نادیده می‌گیرد**. پس راه‌اندازی مجدد با فلگ، **الزاماً** به یک `--user-data-dir` متفاوت نیاز دارد → یعنی کپی پروفایل → یعنی احتمال از دست رفتن کوکی‌های رمزنگاری‌شده‌ی path-bound.
- **پس حالت approval mode برتر است:** پروفایل واقعی، کوکی‌های واقعی، بدون کپی، بدون بستن کروم.
- **هزینه‌اش:** هر اتصال یک پنجره‌ی «Allow remote debugging?» روی صفحه‌ی کاربر باز می‌کند که باید دستی تأیید شود.
- در این حالت، endpointهای HTTP (`/json/version`, `/json/list`) **عمداً ۴۰۴** برمی‌گردانند. فقط WebSocket کار می‌کند → باید مستقیم `ws://127.0.0.1:<port>/devtools/browser` بدهیم، نه `http://`.
- پورت از فایل `DevToolsActivePort` خوانده می‌شود (خط اول پورت، خط دوم مسیر).

### ۲.۳ ارزیابی پروژه‌های کنترل مرورگر برای ایجنت

| پروژه | نگهدارنده | ستاره | حکم برای ما |
|---|---|---|---|
| `browser-use` | اوپن‌سورس | ۱۱۵k | ❌ حلقه‌ی LLM با ۱۰۰ گام؛ **اضافه‌کشی برای کار قطعی** |
| `chrome-devtools-mcp` | **گوگل** | ۵۲k | 🔶 فقط **زمان توسعه** — کشف سلکتور از کروم واقعی |
| `playwright-mcp` | **مایکروسافت** | ۳۷k | ❌ هنوز `0.0.x` بعد از ۵۴۰ روز؛ MCP برای CLI ما بی‌ربط |
| Stagehand | Browserbase | ۲۴k | 🔶 `observe()` سلکتور **واقعی** می‌دهد — یک‌بار برای کشف |
| **Playwright ساده** | — | — | ✅ **انتخاب درست برای مسیر ارسال** |

**اصل حاکم:** هیچ LLM‌ای نباید در مسیر ارسال نهایی باشد. یک رفتار غیرقابل‌تکرار را به کاری که کاملاً قطعی است و روی پول واقعی اثر دارد اضافه نکنید. آن یک مزیتشان («ترمیم خودکار وقتی سایت عوض شد») دقیقاً همان چیزی است که تاییدیه‌ی انسانی پوشش می‌دهد.

### ۲.۴ محدودیت سایت‌های جدید

**بیت‌جاب و کارلنسر هر دو SPA هستند** → با درخواست ساده‌ی HTTP قابل اسکرپ نیستند و **الزاماً به لایه‌ی مرورگر نیاز دارند**، حتی برای جستجو. این تصمیم‌ساز ترتیب فازهاست.

## ۴. فازهای اجرایی

### فاز ۱ — لایه مرورگر (Browser Layer)

**چرا اول:** پیش‌نیاز سایت‌های SPA و پیش‌نیاز فرم‌فیلر واقعی.

**فایل‌های جدید:**
- `core/browser/__init__.py` — نقطه‌ی ورود عمومی
- `core/browser/profiles.py` — خواندن `Local State`، بازگرداندن لیست پروفایل‌ها با **نام پوشه**، نام نمایشی، و ایمیل
- `core/browser/connection.py` — دو استراتژی اتصال:
  - `connect_live()` — خواندن `DevToolsActivePort`، اتصال با `ws://`، تأیید خودکار prefs
  - `connect_isolated(profile_dir=None)` — پروفایل مستقل Playwright با `storage_state`
- `core/browser/session.py` — مدیریت چرخه‌ی عمر سشن، `context` مشترک، بستن ایمن **بدون کشتن کروم کاربر**

**فرمان جدید CLI:**
- `python run.py browser --list` — نمایش ۱۱ پروفایل با نام پوشه و ایمیل (تشخیص نام‌های تکراری)
- `python run.py browser --test` — آزمون اتصال زنده با راهنمای «Allow را بزنید»
- `python run.py browser --status` — آیا کروم باز است؟ approval mode فعال است؟ پورت چیست؟

**نکات ایمنی که باید رعایت شود:**
- `browser.close()` روی سشن متصل، فقط قطع می‌کند و کروم کاربر را **نمی‌کشد** (تأیید شده در Playwright)
- اگر کروم بسته باشد، پیام واضح بدهد نه استثنای خام
- تایم‌اوت اتصال باید بلند باشد (~۹۰ ثانیه) چون کاربر باید دستی Allow بزند

**تست:** mock کردن ناموفق اتصال، پارس کردن `DevToolsActivePort`، تشخیص نام‌های تکراری پروفایل، انتخاب خودکار پروفایل پیش‌فرض.

### فاز ۲ — سایت‌های جدید (۴ پلتفرم)

**اسکرپرهای SPA (نیازمند لایه‌ی فاز ۱):**
- `core/scrapers/bitjob.py` — بیت‌جاب (AngularJS) → از سشن مرورگر استفاده می‌کند
- `core/scrapers/karlancer.py` — کارلنسر (SPA) → از سشن مرورگر استفاده می‌کند

**اسکرپرهای HTTP ساده:**
- `core/scrapers/guru.py` — Guru.com (HTML)
- `core/scrapers/laborx.py` — LaborX (HTML، بازار ارزی)

**بازآرایی لازم:**
- `core/scrapers/base.py` باید دو نوع اسکرپر را پشتیبانی کند: HTTP و مرورگری. پیشنهاد: `BrowserScraperBase(BaseScraper)` که متد `fetch_via_browser()` را اضافه می‌کند.
- `core/scrapers/query_builder.py` — افزودن دو پلتفرم ایرانی جدید به `IRANIAN_PLATFORMS`
- `config.yaml` — افزودن هر ۴ سایت با نرخ تأخیر مناسب
- `interfaces/cli.py` — افزودن هر ۴ اسکرپر به لیست پلتفرم‌ها

**تست:** پارس هر سایت با HTML/JSON نمونه، آزمایش مسیر مرورگری با mock، افزودن سایت پنجم در تست (تأیید افزونه‌پذیری).

### فاز ۳ — پروفایل فریلنسر (Skill Matrix)

**چرا قبل از ارسال:** پیشنهادها باید به نمونه‌کارهای واقعی اشاره کنند، نه متن کلیشه‌ای.

**فایل جدید:** `freelancer_profile.yaml` (نمونه در مخزن، نسخه‌ی واقعی در `.gitignore`)

ساختار پیشنهادی:
```yaml
identity:
  name: "..."
  hourly_rate_irt: 0
  hourly_rate_usd: 0
  min_project_irt: 0

skills:
  - name: "Telegram Bot Development"
    level: expert          # expert | proficient | familiar
    tools: [aiogram, python-telegram-bot]
    years: 3
    evidence: "ربات فروشگاهی برای ..."   # نمونه‌کار واقعی

portfolio:
  - title: "..."
    url: "..."
    scope: bots
    result: "..."

tone:
  style: "technical-direct"   # technical-direct | friendly | formal
  avoid: ["سلام و احترام", "امیدوارم حالتون خوب باشه"]

scopes:
  preferred: [bots, automation]
  willing:   [scraping, scripting]
  declined:  [translation]
```

**تغییرات در `core/architect.py`:**
- `_build_rule_based_proposal()` از پروفایل نمونه‌کار مرتبط را در متن درج کند
- `_calculate_pricing()` از `min_project_irt` شخصی استفاده کند
- فیلتر اسکوپ‌های `declined` در `core/triage.py`

**تست:** بارگذاری پروفایل، انتخاب نمونه‌کار مرتبط با اسکوپ، بازگشت به حالت پیش‌فرض وقتی پروفایل نیست، فیلتر `declined`.

### فاز ۴ — جریان انتخاب و تایید (Selection Flow)

**هدف:** بعد از اسکن، کاربر انتخاب کند — نه سیستم.

**تغییرات:**
- `core/db.py` — افزودن وضعیت `shortlisted` به وضعیت‌های مجاز
- `interfaces/cli.py`:
  - `python run.py review` — نمایش پروژه‌های جدید به‌صورت تعاملی
  - `python run.py pick <id>...` — انتخاب چند پروژه برای اقدام
  - `python run.py run-queue` — پردازش پروژه‌های انتخاب‌شده
- `interfaces/telegram_bot.py`:
  - افزودن دکمه‌ی سوم `[ 📋 افزودن به لیست اقدام ]`
  - پیام خلاصه‌ی روزانه با لینک به لیست انتخاب‌شده

**تست:** عبور وضعیت new → shortlisted → applied، انتخاب چندگانه، پردازش صف.

---

### فاز ۵ — سلکتورهای واقعی و فرم‌فیلر نهایی

**این فاز همان چیزی است که باگ اصلی را می‌بندد.**

**روش کار:**
1. با `chrome-devtools-mcp` (CLI، بدون LLM) یا ابزار کشف داخلی، به کروم لاگین‌شده وصل شو
2. فرم واقعی هر ۵ سایت را باز کن، ساختار DOM را استخراج کن
3. سلکتورهای **دقیق** را در فایل‌های `*_filler.py` جایگزین کن
4. فرم را با مقادیر آزمایشی پر کن (بدون ارسال) و نتیجه را ببین

**سه حالت ارسال:**
- `--mode manual` — فقط پر کردن؛ ارسال دستی توسط کاربر در مرورگر
- `--mode confirm` — **پیش‌فرض**؛ پر کردن + خلاصه در ترمینال + یک اینتر
- `--mode auto` — پر کردن و ارسال بدون تایید

**فایل‌های جدید:**
- `core/form_filler/bitjob_filler.py`
- `core/form_filler/karlancer_filler.py`
- `core/form_filler/guru_filler.py`
- `core/form_filler/laborx_filler.py`

**تست:** mock فرم واقعی با HTML استخراج‌شده، آزمون سه حالت، آزمون شکست سلکتور و پیام خطای واضح.

---

### فاز ۶ — همگام‌سازی پروفایل سایت‌ها (مستند، ساخته نشود)

**وضعیت: به تعویق افتاده.** فقط مستند شود تا فراموش نشود.

هدف آینده: پر کردن بخش «درباره من»، «مهارت‌ها» و «پورتفولیو» در پروفایل هر سایت از روی `freelancer_profile.yaml`.

دلیل تعویق: کم‌ارتباط‌ترین بخش، بیشترین احتمال تغییر نیاز، و پرریسک‌ترین (تغییر پروفایل عمومی کاربر).

## ۵. ریسک‌ها و نقاط شکست

| ریسک | شدت | کاهش |
|---|---|---|
| تاییدیه‌ی مکرر Allow در هر اتصال | متوسط | نگه‌داشتن یک سشن طولانی‌عمر در طول یک اجرا؛ مستندسازی برای کاربر |
| کوکی‌های رمزنگاری‌شده path-bound در حالت کپی پروفایل | بالا | حالت approval mode پیش‌فرض است؛ حالت isolated از storage_state استفاده می‌کند نه کپی پوشه |
| تغییر ساختار DOM سایت‌ها | بالا | لاگ واضح روی شکست سلکتور؛ ابزار کشف مجدد مستند شود |
| تشخیص ربات توسط سایت‌ها | متوسط | استفاده از پروفایل واقعی کاربر؛ نرخ تأخیر محترمانه |
| وابستگی به LLM در مسیر ارسال | — | **معماریاً ممنوع** — تصمیم قطعی گرفته شد |

## ۷. خارج از دامنه (Out of Scope)

- همگام‌سازی پروفایل سایت‌ها (فاز ۶ — به تعویق افتاده)
- اسکرپ Upwork / Fiverr / Malt (ممنوع — طبق spec اصلی)
- ارسال خودکار بدون هیچ مسیر تاییدی در پیش‌فرض
- استفاده از LLM در مسیر کلیک نهایی ارسال
